# Redis and Cloudinary integration for Hostinger

This application is prepared for automatic GitHub deployment to Hostinger with:

- Storefront: `https://bjelectronics.shop/`
- Administrator portal: `https://bjelectronics.shop/admin/`
- API: `https://bjelectronics.shop/api/`
- Redis-compatible distributed cache: Upstash HTTPS REST
- Product image and video storage: Cloudinary signed uploads

## Architecture

Hostinger Business and Cloud web hosting do not provide a local Redis server. The application therefore uses an external Redis-compatible HTTPS REST service. Redis is used as a cache only: if it becomes unavailable, catalog requests fall back to MySQL and the store remains operational.

Cloudinary uploads are performed directly from the protected administrator browser. The browser requests a short-lived signature from `/api/admin/media/signature`, uploads directly to Cloudinary, and receives a delivery URL. `CLOUDINARY_API_SECRET` remains server-side and is never included in the administrator JavaScript bundle.

## 1. Create the Redis database

1. Create an Upstash Redis database.
2. Select a primary region close to the store's customers and Hostinger runtime.
3. Copy the HTTPS REST URL.
4. Copy the Standard REST token, not the read-only token.
5. Store both values in Hostinger environment variables:

```env
UPSTASH_REDIS_REST_URL=https://your-endpoint.upstash.io
UPSTASH_REDIS_REST_TOKEN=your-standard-rest-token
REDIS_NAMESPACE=bj-electronics:production
REDIS_CATALOG_TTL_SECONDS=300
REDIS_REVIEW_TTL_SECONDS=60
REDIS_REQUEST_TIMEOUT_MS=2500
REDIS_REQUIRED=true
```

The cache stores active product catalog responses and product reviews. Product create/update operations and new reviews invalidate their relevant cache keys automatically.

## 2. Configure Cloudinary

1. Create or open a Cloudinary product environment.
2. Copy the Cloud name, API key, and API secret from Cloudinary settings.
3. Add these Hostinger environment variables:

```env
CLOUDINARY_CLOUD_NAME=your-cloud-name
CLOUDINARY_API_KEY=your-api-key
CLOUDINARY_API_SECRET=your-api-secret
CLOUDINARY_UPLOAD_FOLDER=bj-electronics/products
CLOUDINARY_SIGNATURE_ALGORITHM=sha256
CLOUDINARY_REQUIRED=true
```

Do not create an unsigned upload preset. The administrator uses signed uploads generated by the server.

Supported administrator uploads:

- Images up to 10 MB
- Videos up to 50 MB
- Images receive automatic `f_auto`, `q_auto:good`, width limiting, and Cloudinary CDN delivery
- Uploaded images can be used immediately to create a product

## 3. Configure Hostinger GitHub deployment

Use the repository and branch:

```text
Repository: workspacesarindustriesltd-creator/project-bjelectronics
Branch: main
```

Deployment settings:

```text
Framework: Express.js
Node.js version: 20.x
Root directory: .
Install command: npm ci
Build command: npm run hostinger:build
Output directory: dist
Entry file: index.js
Start command: npm start
```

Import all variables from `deploy/hostinger-business.env.example`, replacing every placeholder with a real secret or Hostinger database value. Do not set `PORT`; Hostinger supplies it.

## 4. Prepare MySQL and administrator access

For a fresh database, import `database/schema.sql`. For an existing database, back it up and run the documented migrations.

Create or update the administrator account after the environment variables are available:

```bash
npm run db:seed-users
```

The administrator login is available only from `/admin/` and uses the configured `ADMIN_EMAIL` and `ADMIN_PASSWORD`.

## 5. Automatic deployment

Hostinger GitHub deployment watches the selected branch. After a successful merge or push to `main`, Hostinger automatically starts a new build and deployment.

When environment variables are added or changed in hPanel, use **Settings & Redeploy** so the new values reach both the build and runtime.

## 6. Verification

After deployment, check:

```text
https://bjelectronics.shop/api/health
https://bjelectronics.shop/api/products
https://bjelectronics.shop/
https://bjelectronics.shop/admin/
```

Expected health response structure:

```json
{
  "status": "ok",
  "service": "bj-electronics-api",
  "dependencies": {
    "database": { "status": "ok" },
    "redis": { "status": "ok" },
    "cloudinary": { "status": "configured" }
  }
}
```

For catalog verification, request `/api/products` twice. The first response should include `X-Cache: MISS`; the second should include `X-Cache: HIT`.

In the administrator portal:

1. Open **Media**.
2. Confirm Redis shows `ok` and Cloudinary shows `configured`.
3. Upload an image.
4. Copy the optimized delivery URL or create a product directly from the uploaded image.
5. Open the storefront and confirm the product image is delivered from Cloudinary.

## 7. Failure behavior

- MySQL unavailable: health check fails and database workflows stop.
- Redis unavailable: health reports `degraded`, catalog requests continue through MySQL.
- Cloudinary unavailable: existing products continue loading; new media uploads are disabled.
- Missing required credentials with `REDIS_REQUIRED=true` or `CLOUDINARY_REQUIRED=true`: runtime startup stops with a clear configuration error.

## 8. Security controls

- Redis and Cloudinary secrets are read only from server environment variables.
- Cloudinary uses SHA-256 signed upload parameters.
- Upload signatures are available only to authenticated administrators.
- Cloudinary API secrets never enter frontend source or production bundles.
- Administrator and API responses remain private, non-cacheable, and non-indexable.
- Static hashed assets remain compatible with Hostinger CDN immutable caching.
