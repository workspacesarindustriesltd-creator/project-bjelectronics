# BJ Electronics production domain configuration

## Canonical production origin

Deploy one Hostinger-managed Node.js Web App and use one canonical HTTPS origin:

- Storefront: `https://bjelectronics.shop/`
- Administrator login: `https://bjelectronics.shop/admin/`
- Protected administrator workspace: `https://bjelectronics.shop/admin/dashboard`
- API base: `https://bjelectronics.shop/api/`
- API health check: `https://bjelectronics.shop/api/health`

`/admin` and `/api` are Express application paths, not subdomains. Do not create separate `admin` or `api` DNS records.

Keep `bjelectronics.shop` as the primary domain. Connect `www.bjelectronics.shop` as an alias and permanently redirect it to the apex domain.

## Current blocking condition

If the domain does not resolve or the application returns HTTP 403, complete the Hostinger custom-domain connection and redeploy the Node.js application. A successful GitHub build alone does not publish the domain.

## Hostinger domain connection

1. Open **Websites → BJ Electronics → Dashboard**.
2. Confirm this website is a **Node.js Web App**, not a static or WordPress website.
3. Select **Connect domain** and attach `bjelectronics.shop` to this Node.js application.
4. Add `www.bjelectronics.shop` as an alias for the same application.
5. Set `bjelectronics.shop` as the primary domain.
6. Enable the permanent `www` → apex redirect.
7. Remove conflicting A, AAAA, or CNAME records left by an older website only when Hostinger identifies them as conflicts.
8. Wait for Hostinger to issue SSL for both names.
9. Open **Settings & Redeploy** and redeploy after the domain and environment variables are saved.

When Hostinger manages the DNS zone, use the records generated by the custom-domain connection flow instead of guessing an IP address. If the domain uses external nameservers, copy the exact records supplied by Hostinger into that DNS provider.

If a backend deployment still returns HTTP 403 after a successful redeploy, run **Settings & Redeploy** again so Hostinger regenerates the Node.js routing file in `public_html`.

## Runtime URL variables

Use origin-only values. Do not append `/admin` or `/api`:

```env
NODE_ENV=production
STORE_URL=https://bjelectronics.shop
ADMIN_URL=https://bjelectronics.shop
PUBLIC_API_URL=https://bjelectronics.shop
VITE_STORE_URL=https://bjelectronics.shop
VITE_ADMIN_URL=https://bjelectronics.shop
OAUTH_CALLBACK_BASE_URL=https://bjelectronics.shop
COOKIE_DOMAIN=
```

A blank `COOKIE_DOMAIN` creates safer host-only cookies. Because the application uses the apex domain for the storefront, admin, and API, a shared parent-domain cookie is unnecessary.

## Required security variables

Generate unique values and add them only in Hostinger environment variables:

```env
JWT_SECRET=replace-with-a-random-secret-containing-at-least-32-characters
ADMIN_VAULT_KEY=replace-with-a-different-random-secret-containing-at-least-32-characters
```

Never reuse either value as the administrator password. Do not commit production secrets to GitHub.

## MySQL variables

Copy the exact database name, username, password, host, and port from the Hostinger database panel:

```env
DB_HOST=localhost
DB_PORT=3306
DB_NAME=replace-with-the-full-hostinger-database-name
DB_USER=replace-with-the-full-hostinger-database-user
DB_PASSWORD=replace-with-the-database-password
DB_CONNECTION_LIMIT=10
```

Use `localhost` only when Hostinger displays it as the database host. Hostinger database names and users commonly include an account prefix; enter the full values.

After the first successful application deployment, run the repository migration and seed commands in the supported Hostinger deployment process:

```text
npm run db:migrate
npm run db:seed-users
npm run db:seed-catalog
```

## GitHub deployment verification

After the production domain is reachable, configure these GitHub Actions repository variables:

```text
HOSTINGER_HEALTHCHECK_ENABLED=true
PRODUCTION_BASE_URL=https://bjelectronics.shop
```

`HOSTINGER_DEPLOY_WEBHOOK_URL` is optional. Keep it unset when Hostinger's native GitHub integration already deploys every successful `main` update.

## Route behavior

- `/admin` permanently redirects to `/admin/`.
- `/admin/` and `/admin/login` serve the administrator login shell.
- Protected `/admin/*` navigation requires a valid administrator session.
- `/api/admin/*` requires a valid administrator role.
- `/admin/*` and `/api/*` return private, non-cacheable, non-indexable headers.
- Unknown `/api/*` routes return JSON 404 responses and never fall back to the storefront.

## Final verification

1. DNS resolves for `bjelectronics.shop` and `www.bjelectronics.shop`.
2. `www` permanently redirects to the apex domain.
3. SSL is valid for both names.
4. `/api/health` returns JSON and reports a healthy database.
5. `/` loads the storefront.
6. `/admin/` loads the administrator login.
7. `/admin/dashboard` redirects to login without an administrator session.
8. Valid administrator authentication opens the dashboard.
9. Customer authentication cannot access `/api/admin/*`.
10. GitHub CI and Hostinger Deployment workflows succeed for the deployed commit.
